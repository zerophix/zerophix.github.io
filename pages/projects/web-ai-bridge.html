03
Lifecycle

请求生命周期

POST /ask 从进入 Bridge 到拿到回答的完整链路——每一步都有超时、探针与降级出口。

  1. 01

    解析与钳制 _handle_post_ask

    platform（默认 chatgpt）、prompt、timeout（默认 300s，BRIDGE_REQUEST_TIMEOUT），按 PLATFORM_MIN_TIMEOUT 向上钳制（deepseek 60 / kimi 300 / claude 180 / 其余 120）。Gemini 特例：\n+ 折叠为空格。

  2. 02

    校验 prompt_validator.validate()

    滑动窗口限流（60s，chatgpt 30/min、其余 20/min）→ 结构去重（去标点小写后的 MD5 指纹，TTL 60s，≥15 字符，缓存 50 条）→ 黑名单 / 低信息量 / 长度 → 三层代码上下文检查（当前 shadow 模式只记日志）。

  3. 03

    结果去重 core._check_dedup

    key = platform:::conversation_id:::normalized_prompt，TTL 60s；命中直接返回（流式路径合成一条 done 流）。

  4. 04

    标签页解析 _resolve_tab_for_conversation / _resolve_target_tab

    会话优先按 URL 匹配（/c/{platform_conversation_id}）；否则优先级 tab_id → 同平台空闲已连接 → 已连接 → 已断连标签（重载唤醒，DEC-191 绝不盲建）。无标签 → {"error":"no_extension"}。

  5. 05

    登记 pending _register_pending

    request_id = uuid4 + threading.Event；并发上限 MAX_PENDING = 5，超限返回 too_many_requests；写入 trace（bridge_received）与状态机执行记录。

  6. 06

    预检 + 发送 _preflight_cs → tab_ws.send

    先发 get_chat_state 探针（2s 超时 / 1 次重试，DEC-166，失败只记 cs_probe_failed 不拦截），再 CS 直连 WS 发 {"type":"execute", bridge_driven:true}（SW 路由已删除，DEC-129）。

  7. 07

    双定时器 timer_service + ack 窗口

    extension_timeout 总闹钟；20s 内没收到 ack 即提前超时。Kimi 例外：stop 仍显示时按 30s 续期，封顶 600s。

  8. 08

    轮询收集 _poll_and_collect_result

    前 5s 每 0.01s、之后每 0.1s 检查 event；桥驱动模式下由 _bridge_driven_poll 每 0.5s 发 get_chat_state 拿状态。

  9. 09

    完成 _update_state_completed

    touch 标签、状态机 RESPONSE_COMPLETED、写请求日志 JSON，result 附 trace。

  10. 10

    失败 / 超时恢复 _try_recover_after_timeout

    先做一次 chrome_exec page_context DOM 快照（5s，取末 5000 字符）再放弃，然后 _classify_timeout() 归类。

  11. 11

    条件重试 _handle_post_ask L1581

    错误属 {extension/bridge/transport}_timeout 且 cs_polls < 3（扩展从未应答）且未重试过 → tabs.reload → 最多等 30s（ASK_RETRY_WINDOW）恢复连接 → 换新 request_id 完整重发一次；否则返回原错误。连接关闭 → extension_disconnected，标签置 EXEC_RECOVERING。

  12. 12

    代理区域封锁分支 proxy_switcher / proxy_manager

    错误 + 代理自动开启 + 页面文本命中区域封锁特征 → rotate() 换 IP → 重载页面 → 睡 20s → 重问一次；IP 限制类错误最多 3 次（2s 间隔）。

阻塞 vs 流式

  • 阻塞：POST /ask → await ask_platform()，HTTP 请求等到回答结束。
  • 异步：POST /ask/start → asyncio.create_task，立即返回 {stream_id}。
  • 拉取进度：GET /ask/progress?stream_id=（JSON）或 GET /ask/stream（SSE）。
  • SSE 重分块：桥只存累计文本，按长度差发 delta（chunk = text[last_length:]），event: message / done，0.5s 超时轮转。
  • MCP 不阻塞 HTTP：_ask_bridge_sync 走 /ask/start + 每 0.1s 轮询 progress，并检查 cancel_event 支持取消。

Algorithms

核心算法与机制

网页 AI 没有 API 回执，「回答什么时候结束」只能靠推断——这是整个系统最硬的问题。以下按真实实现类拆解。

1. 回答完成检测状态机 最难的一块

core._bridge_driven_poll · PlatformAdapter.detectBusy · 每 0.5s 一次 get_chat_state（单次 DOM 读，免疫定时器节流）
WAIT_GENERATION→ GENERATING→ STABLE→ COMPLETE · 基线守卫 8s · 40s 无响应
Path A见过生成 + stop 消失 + 文本稳定 + 新鲜
Path Bstop 仍显示但文本稳定（ChatGPT 长回答兜底）
Path C有 newTurn、无 stop/gen 但新鲜稳定（短回答）
Path D完全无信号（豆包）——新鲜稳定即完成
Shortcutcompleted && newTurn && text && isFresh 直接返回
状态机
WAIT_GENERATION → GENERATING → STABLE → COMPLETE；只在 isFresh（当前文本哈希 ≠ 提交基线哈希）时更新 best_text，避免读到旧回答。
输入信号
由各平台适配器采集：stop（停止按钮可见）、state（忙碌）、newTurn（轮次数 / turnKey / messageId 变化）、evenKey（最大偶数轮索引）、completed（平台自带完成属性）、hashChanged、stable。hash = text.slice(0,100) + '|' + text.length。
完成路径
全部要求 stable_polls ≥ 3（文本连续 3 次不变 ≈ 1.5s 静止）；快捷路径 completed && newTurn && text && isFresh 直接返回，跳过 3 次静止窗口——细节见上方 A–D 图例。
基线守卫
等待 baseline_ready 最多 8s；回传 request_id 不匹配 → 强制 isFresh=false, text=''，防止读到上一轮残留（DEC-146/147）。
无响应
40s 既不新鲜、也不生成、也无文本 → no_response_detected 失败。
自适应退避
_poll_interval(n) = min(0.5 × 2^(n//5), 2.0)——0.5s 起步，每 5 次未变翻倍，封顶 2s；连续 60 次未变（≈30s）发一次 ping 唤醒，绝不 reload（会打断生成）。
超时兜底
① 返回 best_text 且标 truncated:true；② chrome_exec page_context 抓 DOM 快照（5s，取末 5000 字符）；③ Kimi 专属 kimi_control {"action":"extract_last"} 读思考区。
Kimi 续期
stop/state 仍显示且无文本时，按 30s 一档续期、封顶 600s（产品反思：STOP 是终极完成信号，长思考必须等）。
静止窗口 3 次指数退避 ×2/5 次单次 DOM 读基线哈希守卫三级超时兜底

2. 降级与重试级联

core._classify_error · _try_recover_after_timeout · proxy_switcher
级联顺序
探针(2s) → execute → ack 窗口(20s) → 总超时 → DOM 快照恢复 → 归类 → 条件重载重试(≤30s 等待 + 单次重发) → 放弃。
错误分类
_classify_error() 分 fixable（登录 / 校验类，重试无用）与 retryable（超时 / 派发 / 无标签）。
重试守门
只有 cs_polls < 3（内容脚本从未应答，说明是链路问题而非生成慢）才值得 reload 重发，避免重复提问烧额度。
区域封锁
代理自动模式下命中 region_blocked(page_text) → 换 IP → 重载 → 睡 20s → 重问一次；IP 限制类 execute_with_retry 最多 3 次 / 2s 间隔。
fixable vs retryable单次重发

6. 限流与并发控制

prompt_validator · config · ExecutionQueue · tab_registry
滑动窗口
_RATE_WINDOW = 60s，每平台配额 PLATFORM_RATE_LIMIT（chatgpt 30、其余 20），默认 20。
防封间隔
辩论同平台两次提问强制随机 2–5s 间隔（MIN_GAP_MIN/MAX，DEC-142）。
在途上限
MAX_PENDING = 5；看门狗每 5s 扫描，超 REQUEST_TIMEOUT 的 pending 清理，僵尸 1h 回收。
串行点
内容脚本侧 ExecutionQueue 单飞行队列（单项超时 130s，DEC-130 防死锁）——服务端不锁每标签，靠它保证同页不并发写 DOM。
实现要点
后端没有 Semaphore，只有 asyncio.Lock / threading.Lock；跨标签并发只由 MAX_PENDING 与限流器约束。
滑动窗口随机 2–5s单飞行队列

7. 去重、关联与流式重分块

prompt_validator · core._check_dedup · DedupMiddleware · request_id
三层去重
① 提问指纹：去标点/大小写/空白后取 12 位 MD5，TTL 60s、50 条；② 结果缓存 key platform:::conversation_id:::normalized；③ 内容脚本 DedupMiddleware 用 executing/completed 两组 taskId Set。
关联
每个请求 request_id（uuid4）贯穿 wire 上的 id/request_id，response、ack、chat_state、trace 全部按它归位；状态机 PROMPT_SENT → ACKED → RESPONSE_COMPLETED|TIMEOUT|DISCONNECTED → CLOSE。
流式重分块
